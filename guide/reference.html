Start with the whole systemFOUNDATIONS

The goal

Explain it, then change it.

Follow the lessons in order once. Afterward, search by task: add an app, rotate a token, recover a generation, or debug DNS. Mark a lesson understood only when you can answer its question in your own words.

The boundary

Source is not the running system.

This guide describes the revised repository. Settings become active only after activation; boot changes may require a reboot. The simulators never change your machine.

What the names mean

Nix is a package manager and expression language. Nixpkgs is a package collection and library. NixOS uses Nix to describe an operating system. Home Manager describes your user environment. A flake gives the project inputs and named outputs. devenv gives each development project its own tools and services.

A laptop has more than one kind of state: configuration source, installed software, running services, personal data, credentials, and firmware. Nix describes much of the first three. It does not turn your documents, databases, or firmware settings into rollback-safe Nix values.

Your system’s shape

flake.nix → shadow/default.nix → modules/nixos/
                              → shadow/home.nix → modules/home/
encrypted-secrets/ → sops-nix → protected files in /run
guide/ → this offline learning interface

Shadow is one Razer Blade 14 with AMD integrated graphics and NVIDIA graphics, Niri and Noctalia on Wayland, a tmpfs root, and LUKS-encrypted Btrfs storage. Hardware facts live in shadow/; reusable capabilities live in modules.

The important habit: locate the owner of a behavior, edit its source, evaluate, build, test, then activate. Do not begin by editing generated files under /etc or the Nix store.

Read the Nix languageFOUNDATIONS

A Nix file is an expression that evaluates to a value. Common values are strings, numbers, booleans, paths, lists, attribute sets, and functions. An attribute set is a mapping of names to values; it is not a shell script. Nix is lazy: values are evaluated when needed.

{ pkgs, lib, ... }:
let
  tools = [ pkgs.ripgrep pkgs.fd ];
in
{
  home.packages = tools;
  programs.fish.enable = true;
}

{ pkgs, lib, ... }: is a function that accepts an attribute set. The module system supplies these arguments. ... permits additional arguments. let … in … introduces local names. Lists use spaces between items. Attribute assignments end in semicolons. home.packages is a nested attribute, equivalent to home = { packages = tools; };.

Patterns you will actually edit

  • ./file.nix is a path relative to the file containing it.
  • import ./flatpak-apps.nix evaluates that expression. A module’s imports = [ … ]; asks the module system to include modules; this has a different job.
  • inherit appId; means appId = appId; using the surrounding value.
  • app.origin or "flathub-verified" supplies a fallback when the attribute is missing. This is not boolean OR.
  • map (x: …) list transforms a list. lib.mapAttrsToList transforms named entries into a list.
  • a // b shallowly merges attribute sets with right-hand keys winning. It is not the module system’s recursive option merge.
  • "${username}" is interpolation: insert a value into a string.

Why a package name sometimes needs pkgs.

pkgs is the package set. pkgs.ripgrep selects a package from it. with pkgs; [ ripgrep fd ] brings those names into scope for that expression. Prefer explicit names when scope would be confusing.

What purity means here

Pure evaluation avoids silently depending on unrelated machine state. Flake inputs and tracked files define the source. This helps reproduce a build, but cannot freeze internet services, external Flatpak updates, mutable databases, or firmware behavior.

Modules, options & mergingFOUNDATIONS

Modules contribute definitions to named options. The module system checks types and combines definitions according to each option’s rules. Package lists normally combine; contradictory ordinary scalar definitions normally produce an error rather than silently choosing the last file.

config is the evaluated configuration. pkgs provides packages. lib provides module helpers. options describes the available option declarations. Your inputs and username arguments are passed from the host composition, not magically available in every unrelated Nix project.

imports = [ ./power.nix ./audio.nix ];
services.upower.enable = true;
some.option = lib.mkDefault "fallback";
some.option = lib.mkForce "deliberate override";

mkDefault gives a low-priority default. mkForce overrides weaker definitions; use it to resolve a specific ownership conflict, not to hide an unexplained error. mkIf conditionally contributes definitions while allowing the module system to resolve dependencies. Read an option’s type and upstream module before assuming the merge behavior.

Shadow’s import boundary

shadow/default.nix imports external NixOS modules and selects system domains. shadow/home.nix selects Home Manager domains. A system module should not reach across and import user modules. For example, installing a desktop integration service belongs to NixOS; your browser settings belong to Home Manager.

A default.nix inside a domain is an explicit aggregator. Files omitted from its import list do nothing. Local AI currently illustrates this: its module exists, but its import is parked, so the system does not automatically build or start it.

To inspect the effective value: nix eval /saved/nixos-config#nixosConfigurations.shadow.config.networking.firewall.enable. Source comments explain intent; evaluated values establish what the module graph actually produces.

Flakes, locks & trustFOUNDATIONS

flake.nix describes inputs and outputs. flake.lock records resolved revisions and hashes. The unstable channel URL is a moving source, but the lock records the revision you actually use. Updating inputs changes that pin; it does not immediately change the running system.

The host output is nixosConfigurations.shadow. Its config.system.build.toplevel is the complete system derivation. The formatter is exposed separately, and the Gitleaks source scan is a check. These are named outputs selected with the # part of a flake reference.

delta = {
  url = "github:zed-industries/delta-nix";
  inputs.nixpkgs.follows = "nixpkgs";
};

follows aligns Delta’s Nixpkgs with the system’s packages and graphics stack. It avoids an unnecessary independent package-set pin. It is appropriate where upstream supports it; do not apply it blindly to every input. Some projects require their own compatible dependency revisions.

Three different kinds of trust

  • A source hash establishes identity of fetched content. It does not prove that code is harmless.
  • A cache public key verifies signatures on substituted build results. Private signing keys belong to the cache operator.
  • Nix trusted-users grants powerful daemon permissions. Shadow trusts root, not the wheel group. You do not need root-equivalent Nix trust just to use a declared binary cache.

Git-backed flakes exclude untracked new files. Use git add for new module files before evaluation; staging is not committing. Read the lock diff after an update. Delta updates through its official input, and its packaged updater is disabled by upstream.

Check → build → test → switchDAILY WORK

Evaluation computes the configuration and derivations. Building realizes the required store paths, using caches where possible. Activation updates system links, service definitions, users, and managed files. Booting loads the selected kernel/initrd and starts the generation from cold state.

Action Changes running system? Meaning
sys-check No Evaluate and run declared checks.
sys-build No Build the system with nh.
sys-test Yes, temporarily Activate without selecting it as the default boot generation.
sys-switch Yes Activate and select the generation for future boots.
sys-update No Update flake inputs only.

For kernel or graphics-driver changes, a temporary test cannot fully validate the boot path. Review, build, arrange recovery, select the generation for boot, then verify after reboot. A service restart can disrupt ongoing work even if the change is reversible.

cd /saved/nixos-config
git diff
nix fmt
git diff --check
nix flake check
nix build .#nixosConfigurations.shadow.config.system.build.toplevel --no-link
sudo nh os test /saved/nixos-config

After temporary activation, check the affected behavior: fresh login for authentication changes, IPv4/IPv6 DNS for networking, actual app launch and data access for sandbox changes. Keep an authenticated terminal and an older boot generation available. Switch only once the result is understood.

What rollback does not restore

A previous generation restores package/configuration references. It does not rewind database migrations, documents, removed files, tokens revoked at a provider, Flatpak app data, or firmware enrollment. A configuration rollback is different from a data restore.

Where to add somethingDAILY WORK

Start with the behavior you want. A device driver or system service belongs to NixOS. A configured personal application belongs to Home Manager. A compiler version for one project belongs to devenv. An ordinary sandboxed desktop app usually fits the Flatpak catalog.

Change Place
Flatpak app + exceptions modules/nixos/services/flatpak-apps.nix
Configured native application modules/home/programs/
Plain GUI / CLI / shared dev tool modules/home/packages/
Launcher for local AppImage modules/home/desktop/local-apps.nix
File type default modules/home/desktop/xdg.nix
System service Relevant modules/nixos/ domain

Configured modules install their own applications when appropriate. Do not repeat Delta, Brave, or KeePassXC in a plain package list. Delta now comes from the official input with its own desktop entry; the old custom wrapper is removed.

The Flatpak catalog is intentionally ordinary Nix data, not a custom module framework. The service adapter derives installation and overrides. Preservation derives data directories from the same entries. Native applications still need their own persistence declarations because there is no reliable universal rule for where every native app writes.

Check for duplicates

rg 'application-name|application.id' modules shadow flake.nix

Occurrences can have legitimate roles: installation, settings, MIME defaults, and persistence. The aim is one owner per role, not one occurrence of every name. Removing an app’s install entry is separate from deleting its data.

Add & manage a FlatpakDAILY WORK

The catalog’s keys are application IDs. An empty entry uses the default verified Flathub remote and retains its data under ~/.var/app/<id>. origin chooses a different remote. overrides declares permissions and environment changes. persist = false; is used for theme extensions with no application state.

"org.example.App" = {
  origin = "flathub";
  overrides.Context.filesystems = [ "xdg-download:ro" ];
};

This is a shape example, not an installable app recommendation. Look up the actual ID, publisher, supported branch, and required permissions before adding it. Verified publishing identifies the publisher; it does not guarantee harmless code or a narrow sandbox.

After editing

  1. Review the app’s upstream permissions and expected workflows.
  2. Format and evaluate the repository.
  3. Build, then activate when ready.
  4. Confirm installation and launch it.
  5. Check file selection, downloads, audio, camera, screen sharing, and persistence after reboot where relevant.
flatpak list --app --columns=application,origin
flatpak info --show-permissions org.example.App
flatpak override --system --show org.example.App
flatpak override --user --show org.example.App

System and user installations are distinct. This repository owns the system installation, including managed override files. Manual system installs can be removed by reconciliation; manual user installs do not automatically gain declared persistence. A user override may take precedence over system policy and must be inspected when behavior differs.

strictFilesystems = true; opts into resetting inherited filesystem grants before applying read-only GTK theme access and this entry’s explicit paths. It is enabled for EarTag, Upscaler, Cine, and Nocturne. Other apps retain their existing narrower manifest permissions until their workflows are reviewed.

The daily Flatpak timer updates apps independently of flake.lock. NixOS generation rollback does not restore a frozen Flatpak application/data snapshot. Removing the catalog entry stops managing its persistence, but old backing data under /saved should be removed only after a deliberate data review.

Understand app permissionsDAILY WORK

Flatpak separates an application from much of the host, then grants capabilities. Filesystems expose paths; sockets expose display/audio interfaces; devices expose hardware; shared namespaces permit networking or IPC; D-Bus policy permits named services. Every grant should match a task the app needs.

xdg-download:ro gives read-only Downloads access. Without :ro, a filesystem grant normally permits writing. dri exposes graphics devices. all is much broader and is retained for specific apps requiring direct device access. An XWayland exception trades isolation for compatibility.

Two different filesystem policies

Denying host and home removes those broad grants. It does not remove narrower inherited permissions such as Documents. A filesystem reset removes inherited path grants before rebuilding the intended allowlist. Per-app policy needs testing; some applications use portals well, while others expect direct folders.

A portal lets the desktop mediate a request, such as selecting a file or sharing a screen. Granting a directory permanently is different from selecting a file through a portal. Previously granted portal access can outlive a single dialog. A network permission is usually all-or-nothing, not a domain allowlist.

Why not block everything globally?

Apps can fail before showing a helpful error: missing GPU access, incompatible Wayland support, camera access, or document paths. Reduce capabilities deliberately, test the actual task, and keep an explicit exception when needed. Isolation must remain understandable.

What about native apps and AppImages?

Native apps do not become sandboxed merely because Nix installs them. AppImage compatibility also does not itself confine an app. They run with their process’s normal user permissions unless another sandbox or enforced policy applies.

What survives a rebootSTATE & IDENTITY

Shadow’s root is a 4 GiB tmpfs. Its contents disappear on reboot unless a path is backed by persistent storage. LUKS protects a Btrfs filesystem whose /nix, /saved, and swap subvolumes survive.

NVMe → LUKS2 → Btrfs
                  ├─ /nix    package store
                  ├─ /saved  selected system/user data + repository
                  └─ /swap   encrypted disk swap
RAM → /            temporary root

Preservation exposes selected backing directories/files at the paths applications expect. Declaring a path describes that relationship; it is not a backup. The authoritative declaration is modules/nixos/storage/preservation.nix. Direct paths already under /saved, such as the repository and deployment identity, do not need another preservation mount.

Important choices

  • Documents, Projects, Books, media, keyring state, browser state, editor data, and selected desktop state are retained.
  • Downloads is intentionally temporary. Move valuable downloads into a retained directory.
  • Flatpak directories derive from the catalog. Theme extensions are excluded.
  • KeePassXC settings and the Rust Book browser profile are now retained with private directory modes.
  • Runtime decrypted files under /run/secrets remain ephemeral.
  • Logs retain up to seven days / 128 MiB. Core dumps are disabled.

Removing a preservation entry does not erase its backing directory. Conversely, deleting the backing directory destroys data independently of a configuration rollback. New preservation mounts also need migration care: data created in an unpreserved home path before activation should be backed up and checked before a mount hides or replaces that view.

Why root:root 0700 or aqua:users 0700?

Ownership selects who controls a file. Directory mode 0700 permits only its owner to traverse it. File mode 0600 permits owner read/write; 0400 is owner read-only. Mount parents need correct ownership too. Permissions reduce access but do not protect against root compromise.

Every key has a different jobSTATE & IDENTITY
Identity Purpose What is public?
LUKS credential Unlock encrypted disk storage Disk-format metadata, not the unlock secret
age identity Decrypt SOPS-encrypted material Recipient starting age1…
WireGuard key Authenticate a tunnel peer The corresponding VPN public key
SSH key Authenticate SSH user or host The public SSH key
Cache signing key Verify substituted Nix results The cache verification key
Secure Boot key Establish trusted boot signatures Enrolled verification certificates

Your age setup has two independent private identities. Aqua’s editing identity is under ~/.config/sops/age/keys.txt, backed by retained home state. Shadow’s deployment identity is /saved/var/lib/sops-nix/key.txt, protected for root. Their public recipients are in .sops.yaml.

SOPS encrypts each file’s data with a data key and wraps access for the configured recipients. In your setup either private identity can decrypt. Having two recipients is recovery redundancy, not a requirement to provide both keys together.

Adding a VPN or token normally reuses the existing age recipients. The VPN may bring its own WireGuard key; that does not require a new age identity.

A public recipient is safe to commit, but authorizing it is a policy decision: it names an identity that may decrypt. Never paste an age private identity into chat, a shell argument, a Nix string, or Git. Back up at least the editing identity with independent encryption off the laptop. Encrypting its only backup to itself makes recovery circular.

When do age identities change?

When an editing or machine identity is replaced, compromised, or newly authorized. Change the recipients, rewrap affected ciphertext with SOPS updatekeys, verify deployment, and rotate compromised provider credentials when necessary. An old private key may still decrypt old Git revisions.

Add, deploy & rotate a secretSTATE & IDENTITY

age supplies identities. SOPS encrypts and edits versionable secret files. sops-nix decrypts declared secrets during activation, assigns ownership/modes, and exposes runtime paths. An encrypted archive without a consumer is not an active service configuration.

Your deployed secrets

The user password hash is decrypted early using neededForUsers. Nix configuration is decrypted for Aqua and linked into the home configuration. The Wallhaven token is inserted into a runtime Noctalia template. GitHub and WireGuard ciphertext were archived separately; The networking stage exposes the archived VPN as a protected runtime file for native NetworkManager import.

Your new everyday helper

secret list
secret status example
secret add example /private/path/example
secret add-token example
secret edit example

add refuses an existing target and a plaintext source inside this repository. add-token uses a hidden local prompt. New ciphertext is published atomically without overwriting another writer’s file. list and status do not reveal values; edit deliberately opens plaintext in your local editor. Adding ciphertext still requires a consumer.

Add a file-shaped secret

cd /saved/nixos-config
sops encrypt --filename-override encrypted-secrets/example.enc   --input-type binary --output-type binary   --output encrypted-secrets/example.enc /private/path/example

Keep the plaintext source outside the repository. Then declare the consumer:

sops.secrets.example = {
  sopsFile = ../../../encrypted-secrets/example.enc;
  format = "binary";
  owner = "service-user";
  mode = "0400";
};
# Use config.sops.secrets.example.path in a file-valued service option.

The owner and path depend on the actual service. Check that the option reads a file at runtime. Do not use builtins.readFile on plaintext or interpolate an actual credential into a Nix setting: evaluated strings may enter the world-readable store.

Why templates are safe here

The tracked Noctalia TOML contains a token marker. Evaluation replaces it with an opaque sops-nix placeholder, then activation inserts the plaintext into a protected runtime file. Edits to that generated file are temporary; durable edits belong to the tracked template. A token can still be copied by its consuming app, so runtime host security remains important.

Rotation and recovery

If a provider token leaked, revoke/rotate it at the provider. Re-encryption cannot revoke it. If one age identity is lost, the other can rewrap secrets for a replacement. If both are lost and no independent backup exists, public recipients cannot reconstruct the keys. A KeePass database is already encrypted and mutable; back it up directly rather than wrapping every change in SOPS.

Changing your login password

Users are declarative. A passwd change is not authoritative across activations. Generate a new password hash through a hidden local prompt, encrypt it into the password-hash ciphertext, build and test while keeping an authenticated recovery terminal, then verify fresh login and sudo before switching. Also consider whether the login keyring password needs a coordinated update.

DNS, VPN & the firewallNETWORK & PROTECTION

DNS translates names to addresses. DNSCrypt/DoH encrypts queries to a resolver. DNSSEC provides validation-related assurances about DNS data, not secrecy. HTTPS protects an application connection. A VPN tunnels routed traffic to another network. A firewall allows or rejects traffic according to rules.

Encrypted DNS is not anonymity: the resolver still sees queries, and connection destinations can reveal activity. A VPN moves trust to the VPN operator; it does not make logged-in web accounts anonymous. Temporary IPv6 addresses and randomized Wi-Fi MACs reduce some stable network identifiers but do not replace routing or app privacy.

Shadow’s ownership

NetworkManager manages connections. dns = "none" keeps it from replacing the DNS policy. DNSCrypt provides the system resolver. Browser-internal encrypted DNS can bypass that system path, so inspect browser settings when testing. Split-DNS corporate VPNs need deliberate integration rather than assuming a fixed public resolver fits them.

The revised configuration listens on both 127.0.0.1 and ::1. Cloudflare and Scaleway remain the deliberately selected resolvers: their catalog stamps advertise DNSSEC, no logging, and no filtering. The require_* settings apply only if automatic selection replaces server_names, so they are not presented as enforcement on those named providers. Resolver bootstrap and endpoint resolution still need network access before the tunnel can connect. Captive portals and filtered networks can behave differently, so connection testing matters.

Firewall direction matters

Closing inbound ports does not block ordinary applications from making outbound connections. A service bound to 127.0.0.1 is local; 0.0.0.0 means all IPv4 interfaces. A broad bind plus a firewall is a different design from a loopback-only service.

Kavita is now configured for loopback only and starts on demand. Its Books mount is read-only, state remains writable, and its old Wi-Fi firewall opening is removed. Open http://127.0.0.1:8083 after starting it with book_library on. Sharing it later requires a deliberate bind/firewall change. A development server’s convenience flag --host 0.0.0.0 should be intentional. IPv6 must be considered separately from IPv4.

Add & operate a VPNNETWORK & PROTECTION

The desktop controller remains NetworkManager. A WireGuard configuration includes a local private key, address, peer public key, endpoint, and allowed IP ranges. Allowed IPs help select which peer handles which destinations; routing rules decide how traffic reaches the interface. These are not equivalent to a kill switch.

Use the native NetworkManager workflow

nmcli connection show
# Only if this profile is not already present:
sudo nmcli connection import type wireguard file /run/secrets/Shadow-BG-20.conf
nmcli connection modify id Shadow-BG-20 connection.autoconnect no
nmcli connection up id Shadow-BG-20
nmcli connection down id Shadow-BG-20

The existing connection is already managed by NetworkManager. Do not import it again merely because you rebuilt. The only new declaration decrypts the existing archive into a root-only runtime file. There is no custom VPN command, Python converter, boot-time import service, or second connection controller. Use the desktop network controls for everyday connect/disconnect.

The safe addition workflow

  1. Obtain the provider configuration through its trusted channel; keep it outside Git.
  2. Encrypt it using SOPS and the existing recipients.
  3. Declare a SOPS runtime file and import it through NetworkManager only if a new profile is needed.
  4. Leave autoconnect off until the profile is verified.
  5. Connect through the desktop network controls or nmcli.
  6. Verify IPv4, IPv6, DNS, endpoint reachability, and intended LAN access.

modules/nixos/security/secrets.nix declares the encrypted archive’s runtime path. To add a second VPN, encrypt its provider file, add an equivalent secret declaration with a unique .conf path, and import it through NetworkManager. The protected NetworkManager connection directory is already preserved across reboot. Importing is an explicit operation; rebuilding does not alter the currently connected VPN. Imported profiles need their autoconnect preference reviewed before relying on their behavior.

Full tunnel, split tunnel, and fail-closed

A full tunnel aims to route general internet traffic through the VPN. A split tunnel covers selected destinations. A fail-closed policy blocks unwanted traffic when the tunnel is absent; it must retain exceptions for VPN endpoint access, necessary DNS bootstrap, and whatever local networking you choose. It cannot be safely inferred just from the existence of a WireGuard interface.

With the present system resolver ownership, do not assume the provider’s DNS field automatically becomes the system resolver. It may be ignored by the existing policy. Before claiming privacy, test DNS routing and browser DNS, and check that IPv6 does not take an unintended path. The configuration does not claim a verified kill switch.

What changes when you add a second VPN?

Usually a new provider config/ciphertext and profile entry. Keep names unambiguous, avoid simultaneous competing default routes, choose autoconnect explicitly, and connect one at a time until you understand the routing. Reuse the existing age identities.

Security without magic labelsNETWORK & PROTECTION

LUKS protects retained data while the disk is locked. It does not block malware running as you after login. SOPS protects selected secrets in Git/store copies, but applications consuming them can read them. An ephemeral root removes undeclared root state after reboot, while preserved histories and app profiles remain.

USBGuard controls USB device authorization. Its built-in allowlist is essential: blindly blocking those devices can break the keyboard, camera, and Bluetooth. Runtime approval needs a persistent policy path if it should survive activation. Review a device before allowing it.

AppArmor is loaded, but useful protection requires enforced profiles that cover actual workloads. A native app without a profile is not magically confined. Service hardening can restrict writable paths, devices, namespaces, privileges, and address families. Add restrictions with the service’s data and workflow in mind.

Authentication and session details

Root password login is locked; Aqua authenticates with a SOPS-deployed hash and has administrative access through sudo-rs. The greetd login stack unlocks the GNOME keyring. A documented workaround bypasses the nested user-manager PAM call after a deadlock; it must be investigated through actual session tests before removing it.

Niri/Noctalia supplies idle locking and suspend behavior. Locking before suspend must be tested interactively. An unlocked keyring can serve credentials to authorized apps; secret-service access should be granted intentionally.

Boot trust is a separate layer

Secure Boot and TPM auto-unlock are not configured by these stages. Secure Boot signs/verifies boot artifacts; it does not replace disk encryption. TPM unlock links access to measurements/policy and needs a recovery credential. NVIDIA and OpenRazer complicate module-signing/lockdown decisions. Enrollment belongs to a prepared recovery exercise, not a quick cleanup.

The previously exposed Wallhaven token still requires provider-side rotation if that has not already happened. A clean current-source scan cannot prove it was revoked or that old Git history contains no secrets.

Project environments & editorsOPERATIONS

Home Manager provides shared tools such as Zed, Delta, devenv, direnv, nixd, nixfmt, statix, and deadnix. Rust, Node, Bun, package managers, formatters, and language servers should follow each project’s requirements in its devenv configuration.

devenv-new my-project
# In an existing project with devenv.nix:
devenv-enable

Your helpers initialize a new environment without replacing an existing one, or add the canonical .envrc if missing. Review .envrc before approval: entering a directory with an approved .envrc can execute its environment setup. Changing its contents requires new approval.

Commit the project’s environment source and locks. Generated .devenv/.direnv state stays out of Git. Retained direnv approvals and devenv state avoid repeating trust setup every reboot. Nix GC roots protect referenced environments.

Editor ownership

Zed’s configuration is divided into settings, languages, LSP definitions, keymaps, and extensions because those are substantial. Delta comes from the official flake; its user configuration/state remains retained. Both still operate with application and agent permissions independent of package reproducibility.

JavaScript and TypeScript use project-local Oxc/Oxfmt and vtsls when available. Save actions use the dedicated Oxc fix action; broad quickfix automation stays disabled. TOML uses Tombi. The repository’s .zed/settings.json recognizes Hugo layouts as Go HTML Template files so formatters preserve template syntax. The ownership and authentication notes live beside the module in modules/home/programs/zed/README.md; provider sessions and credentials remain runtime state.

Local AI costs

The optional local-AI module is currently parked. It would expose a loopback llama-swap endpoint and load models on demand. CUDA compilation can be expensive when Nixpkgs changes; importing the module has build consequences even if the service does not run at boot. Model files belong in retained storage and need their own space/backup policy. Provider-hosted inference has different privacy and account costs.

When adapting another project’s setup, follow the target’s actual lockfile. A Bun project should not inherit pnpm assumptions just because a reference environment uses pnpm.

Recovery, backups & cleanupOPERATIONS

A generation references a particular system closure. Booting an older generation can recover from a broken driver/configuration. A Btrfs snapshot captures local filesystem state at a point in time. An external backup protects against loss of that disk. These mechanisms have different failure boundaries.

These stages do not add external backup jobs or snapshots. Your next recovery priority is a tested encrypted off-device backup of documents, projects, password databases, age recovery identity, and selected app state. Recovery keys cannot exist only on the failed laptop.

Cleanup on Shadow

Friday’s nh cleanup retains recent generations and leaves explicit GC roots intact using --no-gcroots. Nix collects unreachable store paths. Store optimization hard-links identical files afterward. Do not manually delete random store directories or the deduplication index.

Monthly Btrfs scrub verifies checksums across the shared filesystem. A single-device scrub can detect damage but usually cannot repair it without another good copy. SMART gives health indicators, not a guarantee against sudden failure. zRAM compresses memory pages; encrypted disk swap is available as overflow.

If something breaks

  1. Keep the authenticated terminal open and record the symptom.
  2. If an activation change broke a service, restore a known generation or reboot the previous default after a temporary test.
  3. If a boot change failed, select an older generation from the boot menu.
  4. If user data is damaged, use a data backup; switching generations cannot reconstruct it.
  5. If a key is lost, use the independent recovery identity/backup and rewrap secrets.

Reinstallation is different from rebuilding

Disko destroy/format operations erase storage. Do not run them to validate a module. Reinstallation must verify the target disk, restore age identities before deploying encrypted users, and preserve a usable rescue path. The disk layout’s name is not authorization to format it.

User services and the system service manager have different scopes. A graphical-session keyring problem should be tested in that graphical session. A sandboxed tool failing to contact D-Bus or the Nix cache is an execution-environment limitation, not proof the system service is broken.

If the same app symptom appears from both Flatpak and a native package, investigate shared layers such as display, D-Bus, keyring, GPU, and user state. Do not repeatedly replace packages without evidence. Element’s Secret Service integration under Niri is an example of a shared session concern.

Inspect without exposing secrets

Use metadata: service state, paths, ownership, modes, public recipient count, encryption status. Avoid printing private identities, NetworkManager secret fields, environment files, or token-bearing command lines. If a process is listening broadly, its name/working directory is often enough to identify its owner.

Power policy: modern does not mean more daemons

  • PPD: the official reference page identifies documentation version 0.30 (not the installed version). It exposes a small profile API, CPU/platform drivers and actions including AMDGPU panel power management [P][PC]. This is not accurately described as “only CPU throttling.” Actual supported actions/firmware profiles on Shadow need host inspection.
  • TuneD: upstream supports hierarchical profiles and broader device/system tuning [T]. Its README explicitly warns that TuneD conflicts with PPD/cpupower. Upstream tuned-ppd is a PPD-compatible D-Bus frontend to TuneD, not an instruction to run TuneD beside the original PPD [TP]. The fetched controller implements profile mapping and holds, but returns no actions; API compatibility is not identical tuning behavior.
  • TLP: the author’s FAQ explicitly documents TLP 1.9 introducing tlp-pd, offering PPD-compatible profile control and configurable AC/BAT settings [L]. This is a verified upstream claim, not proof of the pinned Nixpkgs version or NixOS module integration. Hardware-dependent charging features are not universal [LI].
  • Decision: PPD already fits the shell and the machine shows working AMD EPP/RTD3. Run the audit’s fixed-brightness, fixed-workload repeated A/B protocol first; display refresh, background jobs and peripherals may dominate. No source supplies a Shadow-specific comparative battery benchmark.
  • Only trial a replacement when a specific unmet control or repeatable inefficiency is identified. Check packages/options in the pinned Nixpkgs, evaluate a mutually exclusive configuration, verify shell/API behavior, and compare measured watts and energy per completed task. Keep rollback to PPD and restore prior profile/settings.
  • Don’t add auto-cpufreq, persistent CPU governors or Powertop auto-tuning alongside a backend. Powertop can help diagnose wakeups interactively, but an indiscriminate autosuspend policy can break USB/audio/networking and obscure which component owns a setting.
  • Battery longevity is separate from runtime: the observed charge ratio suggests wear, not a daemon failure. Prefer supported firmware/charge thresholds if exposed and tested, reduced heat, and measured runtime; do not invent Razer threshold support or force unsupported suspend modes.

NVIDIA: retain the result, not cargo-cult flags

The 615.71.09 NVIDIA RTD3 README matches the observed module version [N]. It requires runtime PM support for all PCI functions and describes fine-grained control, proc diagnostics and video-memory power states. Supported Ampere-or-newer notebooks default to fine-grained behavior through 0x03; this is conditional on the platform, not a blanket promise for all GPUs.

Shadow’s pinned Razer module already defaults PRIME offload, suspend power management and fine-grained PM [H]. Local nvidiaPersistenced = false avoids intentionally keeping the device initialized; upstream specifically warns that persistence with UVM persistence mode disables RTD3 [N]. Do not conflate every persistence setting with that precise warning.

Both observed GPU functions were suspended and video memory was off. Check that this returns after games/CUDA exit and unplugging displays; outputs wired to the dGPU or ongoing workloads can keep it awake. Do not copy the README’s historical pre-5.5 PCI-function removal workarounds. NVIDIA S0ix and whole-system s2idle need separate resume/drain testing, not another RTD3 toggle.

Reliability: backup, integrity and preservation

  1. Backup policy before tooling: agree on recoverable data, maximum acceptable loss and restore time; protect documents/projects, relevant application databases, configuration and secret recovery material. Review exclusions for rebuildable store/caches/game downloads. A broad /saved archive may include highly sensitive keys/tokens and must be encrypted with independently recoverable access.
  2. Off-device plus tested restore: Restic documents that restore overwrites existing files by default [R]. Select a concrete snapshot ID, restore to an isolated adequately sized external directory and verify representative files, permissions and application recovery; do not restore over production or fill the tmpfs root. Add offline/immutable or separately credentialed protection where deletion/ransomware risk warrants it.
  3. Verify repository content: restic check normally checks structure/metadata; restic check --read-data reads all packs [RC]. For large repositories rotate --read-data-subset=1/5 through 5/5 over a defined period. Repeated random samples do not guarantee complete coverage. These are examples after repository credentials are configured, not commands executed by this audit.
  4. Scrub is already present: Btrfs recommends roughly monthly scrub; it detects checksum errors and repairs only from a valid redundant copy [B]. Single-device data may lack that copy. NOCOW data is not data-checksummed; journald commonly uses NOCOW. Scrub is neither fsck nor a backup, and interruption/suspend can require resume handling.
  5. Ephemeral root matters: upstream records scrub progress in /var/lib/btrfs [B]. Inspect whether it is actually persistent, then decide whether progress/history is worth preserving. Similarly inspect installed SMART state, DNS catalog cache and power-profile state locations; don’t persist whole /var/lib indiscriminately. Update the operator guide whenever the persistence contract changes.
  6. SMART is already present: upstream smartd documentation covers NVMe warnings and version/hardware-dependent self-tests [S]. Enablement alone does not prove tests run or warnings reach Aqua. Inspect generated configuration and test the notification path; schedule supported tests on AC and record trends rather than trusting a single “healthy” result.
  7. Keep independent LUKS passphrase/header and SOPS age-key recovery; encrypted disk contents, committed SOPS ciphertext and same-disk snapshots each fail different recovery requirements. Validate recovery media and unlock access before firmware or boot policy changes.

Secure Boot: staged, with recovery first

Lanzaboote explicitly warns of sharp edges and inconsistent firmware behavior [Z]. It fits the declared UEFI/systemd-boot architecture, but host EFI/Secure Boot state was not verified. It signs boot artifacts; that is not a complete defense for a running system, stolen signing keys or mutable persistent state [ZS].

Proposed sequence, not executed instructions:

  1. Verify bootctl status, firmware setup/recovery access and external unlock/recovery material; review hardware-specific vendor/OptionROM requirements.
  2. Pin a reviewed compatible Lanzaboote release; build and inspect signed artifacts before enforcement. Current preparation docs use /var/lib/sbctl as the PKI bundle [ZP]: on tmpfs root it must be deliberately persisted, root-only, encrypted and independently backed up.
  3. Check 1 GiB ESP headroom across retained generations; test NVIDIA/OpenRazer module loading and understand any kernel lockdown/signature implications. UKI signing does not by itself establish a complete out-of-tree module-signing policy.
  4. Enroll only with a proven recovery path. Preserve required vendor/Microsoft trust and dbx; don’t indiscriminately clear all firmware keys [ZE]. Reboot and verify Secure Boot, old/new boot entries, graphics, resume and firmware-update behavior.
  5. Keep manual LUKS unlock initially. TPM measured unlock, PCR policies, optional PIN and recovery fallback require a separate threat model; merely adding tpm2-device=auto is not equivalent to this chain of trust [ZS].

The fetched preparation page contains different example tags (v1.2.0 for lon, v1.1.0 for flakes). These are examples, not evidence of the latest release. No release recommendation or Razer-specific enrollment procedure is asserted here.

Save work first. Do not force unsupported deep sleep or assume hibernation works. Check supported charge-threshold attributes before proposing longevity limits; do not deep-cycle solely for this audit.

Safe update and clarity policy

From /saved/nixos-config, run nix flake check --no-write-lock-file, git diff --check, and nix build .#nixosConfigurations.shadow.config.system.build.toplevel --no-link --no-write-lock-file. Review lock/source diffs before sudo nh os test /saved/nixos-config; test activation does not load a new kernel or undo mutable data changes. Bootloader/kernel/storage changes also need a reviewed boot generation, actual reboot, and recovery media. Never test with destructive Disko commands.

Before weekly cleanup, inspect nh clean all --dry --keep 3 --keep-since 7d --no-gcroots and bootable generations; keep a durable known-good rollback until a new generation passes AC/battery, boot, resume, offload and networking checks. Checklist conventionsREFERENCE

The checklist is maintained in guide/tools.json. It groups related components into compact rows and owns the release-watch links.

  • [x]: the row’s source checks match its Nix declarations.
  • [ ]: a source check no longer matches, or the candidate is explicitly not selected.
  • [?]: inherited options, hardware compatibility or runtime behavior need verification.
  • Monitored: follow development; no deployment claim.
  • ★: generated into the primary release watchlist from the same entry.

Source checks use file paths and regular expressions against comment-stripped source. They describe local declarations, not the evaluated module graph. If you move or substantially rewrite a declaration, update its source check; a missing source file fails the build. Rebuild after configuration edits.

The purpose column gives the brief technical role. Click a component to open its source preview or primary project documentation. Existing research and historical audit notes remain in the reference section.

Add a row only when it represents a major system component or a useful candidate. Put operational detail in reference Markdown and planned work in the roadmap. Runtime results and installed versions require separate measurements.

ArchitectureREFERENCE

Shadow is a single-host NixOS configuration with Home Manager. The technology catalog below owns tool descriptions and decisions; configuration previews and locked revisions are generated from source.

Configuration flow

Layer Source Responsibility
Inputs flake.nix / flake.lock Dependencies and pinned revisions
Machine shadow/default.nix Hardware facts and NixOS module selection
User shadow/home.nix User identity and Home Manager module selection
System modules/nixos/ Boot, storage, security, services and drivers
Desktop modules/home/ Programs, shell, editor and window manager

State flow

NVMe → LUKS → Btrfs → persistent /nix and /saved. The root filesystem is temporary; Preservation restores explicitly selected state. Independent backups provide recovery beyond the laptop.

Change flow

Edit → evaluate → build → temporary activation → review → switch → reboot and verify.

  • One host and one user with direct module imports
  • Declarative system and user configuration
  • Explicit persistent-state ownership
  • Independent backup and restore acceptance: see the roadmap

These marks describe configuration and outstanding work, not live service health.
